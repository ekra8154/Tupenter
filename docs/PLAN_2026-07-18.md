## 1. `blockset` / `itemset` param types

**Vanilla's answer to "block or blockset?"**: two separate argument types.
`BlockStateArgument` = concrete block only (`/setblock`). `BlockPredicateArgument`
= block **or** `#tag`, with `[states]`/NBT filters (`/fill ... replace <filter>`,
`/execute if block`). Vanilla never mixes them in one type — the command picks
the type by what it can consume. We mirror that:

- `block` stays concrete. New `blockset` wraps `BlockPredicateArgument`
  (tab-completes ids **and** `#tags`, binds verbatim text).
- **[my call]** also add `itemset` wrapping `ItemPredicateArgument` — same
  pattern, zero extra design. Both verified present in 1.21.10 mappings with
  `CommandBuildContext` factories.

## 2. Random pick from a tag — `blockset(...)` / `itemset(...)` expression functions

`/setblock ~ ~ ~ $rand(blockset("#c:ores"))$`

- New expression functions `blockset("...")` and `itemset("...")` resolve a
  tag through the live connection's registry access into a **list value** of
  ids. Fabric `c:` tags are ordinary registry tags — free.
- `rand(list)` picks a uniform random element (rand already exists; add the
  1-arg list overload). pick/foreach compose since lists already exist.
- **[my call]** tag is a quoted string (`"#c:ores"`, leading `#` optional)
  because `#` unquoted would fight the expression lexer. EvalContext gets a
  tag-resolver hook so the script package stays MC-free (tests stub it).

## 3. Per-world / per-server script states

The nukeOnDeath guarantee: joining a world you haven't configured runs nothing.

- World key: server address (multiplayer) / level folder name (singleplayer).
- Tick-script master toggle becomes **per-world**, persisted as a map
  `worldKey -> enabled` in the config. Default for an unknown key: **off**
  **[my call — safe default]**.
- Per-script toggles stay global (they're editing state, not arming state);
  the per-world master is the arming switch. `/tupenter scripts on|off|status`
  manages the current world; Mod Menu shows the toggle for the world you're
  in (or explains you're not in one).

## 5. Highlightable (selectable) chat

Why vanilla lacks it: chat is immediate-mode glyph rendering — there is no
text object to select; selection must be built from scratch. Possible: yes.

- Drag in the chat panel -> map to (line, char) via `Font`/`StringSplitter`
  widths -> draw inverted-color overlay -> Ctrl+C copies (plain text,
  formatting codes stripped).
- Scope ladder **[my call]**: (a) char-level selection within one message,
  (b) multi-line range, (c) fall back to whole-message-click-to-copy if the
  glyph math fights back. Toggleable in Mod Menu like everything else.

## 6. `#wait` + lazy interpreter + overlap policy

The clash, named precisely: eager unroll evaluates every `$...$` at
Enter-press, so state reads (`$client.target_block$`) bake before earlier
commands take effect (the /blink failure) — and `#wait` is meaningless if
everything already evaluated. So #wait *requires* the lazy interpreter:

- Parse eagerly to a statement tree (syntax errors still instant), but
  evaluate each statement's markers **just before it sends**. Loop bounds
  check at parse; per-iteration bodies evaluate lazily.
- `#wait 10t|0.5s` = scheduler yield inside the executor's per-tick pump.
- **Resend interplay**: history stores the original line (already true), so
  resending re-runs the script fresh. Overlap policy **[my call]**:
  re-running the *same source line* cancels its still-running instance
  (rapid-fire resend = restart, not stack); *different* lines run
  concurrently; `/tupenter abort` kills all. Caps unchanged.
- `/unroll` on a #wait script shows the schedule with un-evaluated markers
  marked `(lazy)`.
- Design section in SCRIPTING_DESIGN.md first, then executor rework.
